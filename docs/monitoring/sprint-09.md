# Sprint N°10 : Pilotage Docker TUI, détection des conflits de merge, diff des documents riches (.docx / .pdf) et vision multimodale

User Stories :

- US 10.1 : En tant que développeur, j'intègre dans le TUI Go (`src/cli/views/config_view.go`, `src/cli/bridge/client.go`, `src/cli/bridge/python_client.go`, `src/cli/bridge/mock_client.go`, `src/cli/models/types.go`) l'affichage en direct de l'état du conteneur Ollama (`En cours`, `Arrêté`, `Indisponible`) via la méthode `DockerOllamaStatus`, et j'ajoute l'action interactive dédiée `[D]` permettant d'activer ou désactiver instantanément `USE_DOCKER_LLM` et de piloter le démarrage/arrêt du conteneur sans passer par le menu général de modification des variables.

- US 10.2 : En tant que développeur, je sécurise le cycle de vie et le démarrage du conteneur Docker en vérifiant l'état effectif après exécution de `docker compose up`, en affichant un bandeau d'avertissement explicite lorsque le mode Docker LLM est actif mais que le conteneur est arrêté (rappelant le modèle configuré et la commande `docker compose logs -f ollama`), et en déclenchant un échec contrôlé dans `entrypoint.sh` si le modèle ou le serveur ne répond pas.

- US 10.3 : En tant que développeur, je conçois et expose le contrat de données `GitState` (`src/git_commit_release_notes_generator/models.py`) ainsi que la méthode `get_git_state()` dans `GitWrapper`, détectant automatiquement les opérations Git en cours (`merge`, `rebase`, `cherry-pick`, `revert`), les branches et révisions parentes (`MERGE_HEAD`, `head_parents`, `merge_base`), afin de transmettre au modèle de langage le contexte global complet nécessaire pour qualifier avec justesse une fusion de branches ou une résolution de conflit.

- US 10.4 : En tant que développeur, j'enrichis les modèles `ConflictSection` et `ConflictFile` (`src/git_commit_release_notes_generator/models.py`) et j'implémente les méthodes d'analyse avancée dans `GitWrapper` (`get_conflict_files`, `get_conflict_sections`), extrayant les zones de conflit à la fois depuis l'index Git (`repo.index.unmerged_blobs()` avec les stages `:1: base`, `:2: ours`, `:3: theirs`) et depuis les fichiers de travail (parsing des marqueurs standards `<<<<<<<` / `=======` / `>>>>>>>` et diff3 `|||||||`), en conservant les lignes de début/fin, les blocs de contexte environnants (`context_before`, `context_after`) et en prenant en charge les cas particuliers (fichiers binaires, conflits modification/suppression).

- US 10.5 : En tant que développeur, j'étends `GitWrapper` pour extraire automatiquement le texte des documents bureautiques Word (`.docx` via `python-docx`) et Acrobat (`.pdf` via `pypdf`) directement depuis l'object database Git (`repo.odb`), et je génère un diff unifié ligne à ligne (`difflib.unified_diff`) qualifié en `DiffFile` texte normalisé (`is_binary=False`), permettant ainsi au LLM de décrire les modifications rédactionnelles au sein de documents jusqu'alors exclus comme de simples binaires opaques.

- US 10.6 : En tant que développeur, je renforce le contrôle préventif de disponibilité du modèle dans `check_ollama_reachable(validate_model=True)` en interrogeant `/api/tags` pour refuser immédiatement un modèle absent avec une invite claire à `ollama pull`, et j'implémente un module d'analyse visuelle (`src/git_commit_release_notes_generator/ollama_client/vision.py`) exploitant les modèles vision (ex: `qwen3-vl:8b-instruct`) pour décrire les ajouts, suppressions et modifications d'images indexées sous forme d'un patch textuel synthétique `[Analyse visuelle]`.

- US 10.7 : En tant que développeur, je consolide l'infrastructure de tests automatisés en intégrant une suite dédiée de 426 lignes pour les conflits et le merge (`test/test_git_wrapper_merge.py`), des tests d'intégration réels pour les documents Word/PDF et le modèle de vision (`test/test_git_wrapper.py`, `test/test_vision.py`, `test/test_core.py`), 294 assertions dans la suite Go (`test/cli/bridge_test.go`) pour le pilotage et la robustesse Docker, tout en adaptant le workflow CI GitHub Actions (`.github/workflows/ci.yml`) pour installer `python-docx` et `pypdf`.

- US 10.8 : En tant que développeur, j'aligne la documentation technique avec le code en créant les fiches miroirs correspondantes (`test_git_wrapper_merge.md`, `vision.md`, `image_description_system.md`, `test_vision.md`), en enrichissant les pages existantes (`models.md`, `git_wrapper.md`, `conflict_resolver.md`, `docker-compose.md`, `doc_architecture.md`, `README.md`), et en générant la version actualisée de la documentation globale compilée (`documentation.pdf`).


Livrables / DoR & DoD :

- Pilotage interactif du conteneur Docker Ollama intégré à l'écran de configuration du TUI Go (`src/cli/views/config_view.go`), affichant l'état en temps réel (`DockerOllamaStatus`) et proposant l'action dédiée `[D]` avec garde-fous au démarrage et messages d'alerte explicites.
- Moteur d'extraction et d'exposition de l'état Git global (`GitState`) et des conflits de merge (`ConflictFile`, `ConflictSection`) opérationnel dans `GitWrapper`, supportant les stages d'index 1/2/3, les marqueurs de conflits standards et diff3, avec contextes de lignes et gestion des conflits complexes.
- Support complet du diff textuel sur les documents Word (`.docx`) et PDF (`.pdf`) dans `GitWrapper` via extraction Git ODB et conversion en `DiffFile` texte, intégré aux inférences de commit et de release notes.
- Module de vision multimodale `ollama_client/vision.py` et validation proactive du modèle configuré via `/api/tags` opérationnels, générant des synthèses textuelles des modifications d'actifs graphiques.
- Suite de tests unitaires et d'intégration validée : tests Python de merge (`test_git_wrapper_merge.py`), tests de vision (`test_vision.py`), tests de documents riches (`test_git_wrapper.py`), tests Go Docker (`bridge_test.go`) et workflow CI (`ci.yml`) synchronisé.
- Documentation technique MkDocs (`mkdocs.yml`, fiches miroirs sous `docs/`) synchronisée avec le code source et livrable `documentation.pdf` actualisé.
